# KAURAX — Fault Proof Implementation Report

**Date:** 2026-09-08 · **Scope:** trace commitments, one-step verifier, multi-level dispute
game · **Deployed:** nothing

---

## 1. The answer to the question that matters

**Is this production-ready? No.**

**Does KAURAX now have fault proofs? No.**

What exists is a genuine one-step verifier — it executes a disputed instruction on chain and
decides from the result, with no oracle, no signature and no privileged caller — and a
dispute game that narrows to a single instruction and resolves through it. Both work, and
`test_incorrectStorageTransitionLoses` and its siblings prove a dishonest proposer loses.

But it verifies the **KAURAX Verifiable Subset**, and KAURAX blocks are executed by `anvil`
over the full EVM. The verifier cannot adjudicate a real KAURAX dispute, and it is
deliberately **not connected to `KauraxL2OutputOracle`**. Settlement disputes remain
guardian-resolved.

The brief said to say so plainly if production fault proofs could not be completed here.
They could not, for the reason in §2, and this is that statement.

---

## 2. Why — the audit finding that determined the design

[FAULT_PROOF_AUDIT.md](FAULT_PROOF_AUDIT.md) finding **A-2**: KAURAX's state transition
function is not in this repository. `blockchain/l3/src/engine/` holds one engine,
`AnvilEngine.ts`, which drives `anvil` over JSON-RPC. The proposer *reads* a state root from
`eth_getBlockByNumber`; nothing computes one. `grep` finds no component that re-executes a
transaction or replays a block.

A fault proof needs an STF that can be instrumented to emit a per-instruction trace and
re-executed one step at a time on chain. `anvil` can do neither.

The audit also found **A-1**: `AnvilEngine.ts:11` claims the testnet profile uses `op-geth`.
No such engine exists and the profile is never consulted. Not fixed by this work — it is a
documentation defect in a comment, recorded for a separate change.

And **A-3**: the existing game's bisection carries no binding claim structure. The challenger
picks a half without committing to a counter-claim, and `midClaim` is overwritten each round,
so the leaf has neither an agreed pre-state nor a pinned disputed post-state. That is why the
new game is a new contract rather than an added function.

## 5. Two bugs found in this work, by these tests

**A soundness bug in the verifier.** `SSTORE` read the prior storage value to decide whether
the write cost 20,000 or 2,900 gas — and did so **before proving that value**. A prover could
supply a fabricated prior value, change the price, and thereby change whether the step ran
out of gas: a different post-state, reached without ever touching the committed tree. The
differential corpus caught it on `halt-out-of-gas-on-sstore`. The verifier now proves the
leaf before pricing from it.

**A griefing vector in settlement.** The game paid the winner inside `proveStep`. A
challenger contract with no payable fallback made every call to `proveStep` revert, and since
a game at the leaf can be resolved no other way, both bonds were locked permanently — a trade
a griefer would take. Settlement now credits and the payee pulls;
`test_aWinnerThatRejectsEtherCannotFreezeTheGame` locks it in.

Neither was reported by a tool. The first came from a corpus designed to hit halt paths; the
second from writing §7 of [FAULT_PROOFS.md](FAULT_PROOFS.md) and asking what a hostile winner
could do.

## 6. Security assumptions

**What the verifier assumes:** keccak256 is collision-resistant. That is all. It has no
owner, no oracle, no upgrade path and no privileged caller, and it is `pure`.

**What the game assumes:** the verifier is correct; at least one honest party is willing to
play; and that party can get a transaction included before the deadline.

**What is not assumed:** nothing here trusts the proposer, the sequencer, the guardian, or
any signature. `isFaultProof()` returns `true` on this contract and `false` on
`KauraxDisputeGame`, and both are accurate.

**Unchanged elsewhere:** no privileged operation was added, removed or weakened anywhere.
Governance still holds every role it held; the guardian's powers over settlement are exactly
what they were. No admin bypass, no emergency mechanism, no trusted shortcut was introduced —
the new contracts have no privileged functions at all.

## 7. Remaining attack surface

| Surface | Status |
|---|---|
| Nobody submits the step proof at the leaf | **Open.** The claim stands. Submission is permissionless, but an absent or censored challenger loses a dispute it should have won |
| A challenger stalls to the last moment each round | **Open.** Delay of roughly `rounds × RESPONSE_TIMEOUT`. Costs the challenger its bond if wrong |
| Bond sizing | **Not analysed.** Whether griefing is uneconomic depends on deployment values. No figure is claimed correct |
| Verifier correctness beyond the corpus | **Partly open.** 404 differential cases and 256-run fuzz; not exhaustive, and no formal verification |
| Opcodes outside the subset | **Halt**, not approximate — but a program needing them cannot be proved at all |
| Storage model | Flat map, not the MPT. Nothing about accounts, balances or nonces is provable |
| External audit | **None.** |

## 8. Gas

Measured by `test_stepVerificationStaysInsideTheGasBudget`, execution only:

| Instruction | Gas |
|---|---|
| `STOP` | 7,940 |
| `PUSH1` | ~19,200 |
| `ADD` | 36,367 |
| `SLOAD` | 137,987 |
| `SSTORE` | 233,249 |

Add roughly 128,000 gas of calldata for a step that touches storage: a 256-sibling proof is
8 KB at 16 gas/byte. Worst case stays well inside the 5,000,000 budget, and the test fails if
that stops being true.

**Not optimised.** Bitmap-compressing the zero siblings of a storage proof would cut it to a
handful of hashes. Merkleizing the code commitment would stop every proof carrying the whole
program. Neither is implemented.

## 9. Deployment requirements

**Nothing has been deployed. The live testnet is untouched.**

To deploy the verifier and game:

1. `KauraxOneStepVerifier` — no constructor arguments, no owner, immutable.
2. `KauraxFaultDisputeGame(verifier, proposerBond, challengerBond, responseTimeout, claimMaturity)`.
   The constructor rejects zero bonds, a zero timeout, and a maturity at or below the
   response timeout.
3. **No settlement contract changes and no migration.** The new game is not wired to the
   oracle, so `setDisputeGame` is not called and `KauraxDisputeGame` keeps its role.

Bond and timeout values are a governance decision this report does not make.

### 9.1 If it were ever wired to settlement — which it must not be yet

`KauraxL2OutputOracle` depends on a game through one function, `hasLiveGame(uint256)`, so a
future game is installable with `setDisputeGame` (challenger-gated). **`KauraxFaultDisputeGame`
does not implement that interface, deliberately.** Wiring it in before output roots commit to
an execution trace would produce a contract that looked like a fault proof over KAURAX state
while proving something unrelated to it — which is precisely the failure this brief forbids.

The order is: instrumentable engine → output roots that commit to a trace → full opcode
coverage → MPT state model → audit → then wire it in.

## 11. What may and may not be said about this

**May be said:**
- KAURAX has an on-chain one-step verifier that executes a disputed instruction and decides
  from the result.
- It has a permissionless multi-level dispute game that resolves genuine execution
  disagreements through that verifier, with no guardian.
- Both are covered by 404 differential cases against an independent implementation.

**May not be said:**
- That KAURAX has fault proofs. It does not — not over its own state transitions.
- That the verifier covers the EVM. It covers a documented subset.
- That any of this protects a withdrawal. It is not connected to settlement.
- That it is production-ready or audited. It is neither.

The scope is stated on chain: `KauraxOneStepVerifier.coverage()` and
`KauraxFaultDisputeGame.scope()` both return strings naming the gap, so an integrator reading
the deployed bytecode cannot be told only half of it.
