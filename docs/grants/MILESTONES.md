# KAURAX — Milestones

Seven milestones, ordered by dependency. Each has an acceptance test a third party can run
without trusting the KAURAX team.

Effort figures come from [../FAULT_PROOF_ROADMAP.md §6](../FAULT_PROOF_ROADMAP.md) and are
estimates. **No calendar dates are given.** Fault proof work has a long history of missed
dates, and a proposal that quotes one is either padding or has not built one.

---

## M1 — Pin and specify the state transition function

**Effort:** 1–2 engineer-months

KAURAX executes through revm. That is deterministic in practice but not pinned by
specification, and not checked against a second implementation.

**Delivers**
- A written STF specification (EVM version, precompiles, gas schedule, L3-specific rules)
- The pinned EVM version committed on chain and read by the derivation pipeline
- A differential test harness running KAURAX's STF against an independent EVM

**Acceptance:** the harness replays every block of the public testnet through both
implementations and reports zero state-root divergences. A reviewer runs it from a clean
checkout.

**Failure is informative:** a divergence found here is a consensus bug that exists today and
is currently invisible.

---

## M2 — Adopt a proving VM

**Effort:** 3–6 engineer-months · **Depends on:** M1

Compile the pinned STF to MIPS (see the proposal for why MIPS).

**Delivers**
- The STF built for the proving VM, reproducibly
- An off-chain emulator producing instruction-level traces
- Traces for real testnet blocks, byte-identical when regenerated by a third party

**Acceptance:** an independent party checks out the repository, regenerates the trace for a
named testnet block, and gets the same hash the team published.

---

## M3 — Trace commitments

**Effort:** part of M2's 3–6 · **Depends on:** M2

**Delivers**
- Per-instruction state hashing and the Merkle tree over it
- Trace roots committed alongside output roots
- Tooling to produce an inclusion proof for any instruction index

**Acceptance:** given a block and an instruction index, the tool emits a proof that verifies
against the committed root. Wrong index, wrong state, or tampered proof each fail.

---

## M4 — Preimage oracle

**Effort:** 1 engineer-month · **Depends on:** M2

**Delivers**
- The on-chain oracle contract
- Permissionless submission with size and gas limits
- A tested path from "verifier needs preimage X" to "anyone posts X"

**Acceptance:** a party other than the sequencer supplies every preimage a real dispute needs,
using only publicly available data.

---

## M5 — One-step verifier

**Effort:** 6–12 engineer-months · **Depends on:** M3, M4

The largest and highest-risk milestone. Split by instruction class; each class ships tested.

**Delivers**
- `step(preState, proof, preimages) → postState` on chain
- Full instruction coverage
- A differential fuzzing campaign: random pre-states through the verifier and the emulator

**Acceptance:** for a large corpus of random and adversarially chosen instructions the
verifier's post-state matches the emulator's, gas stays under 5,000,000, and calldata under
100 KB. **Coverage gaps are reported, not omitted.**

---

## M6 — Trace bisection and advisory operation

**Effort:** 1–2 engineer-months · **Depends on:** M5

`KauraxDisputeGame` already bisects to a single block. Extend the same loop to instruction
indices and add `resolveWithProof`.

**Delivers**
- Bisection to instruction granularity
- `resolveWithProof(gameId, proof, preimages)`
- **Advisory mode:** the guardian remains authoritative; every verifier outcome is recorded
  and compared
- A challenger agent that detects a bad root and plays the game unassisted

**Acceptance:** on a testnet running invalid proposals deliberately, the challenger wins
without human help, and the verifier's verdict matches the guardian's on every game over a
sustained period.

---

## M7 — Audit and cutover

**Effort:** 3–6 months elapsed · **Depends on:** M6

**Delivers**
- External audit of the verifier, oracle and dispute game
- Public report and remediation
- Removal of `resolve()`'s guardian path
- A revised security model with the guardian gone from the withdrawal path

**Acceptance:** the audit is published including unfixed findings; the guardian can no longer
decide a dispute; [../SECURITY_MODEL.md](../SECURITY_MODEL.md) moves dispute resolution from
TRUSTED to TRUSTLESS with the commit that did it cited.

**This is the only milestone that lets KAURAX use the word "trustless" about its output
roots.** M1–M6 do not.

---

## Reporting

Each milestone closes with a public report: what was delivered, what was not, what was found,
what changed in the plan. **A milestone that fails is reported as failed** — the acceptance
tests above are run and published either way.
